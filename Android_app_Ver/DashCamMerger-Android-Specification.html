This document describes what was actually built, in enough detail to rebuild the app from scratch without the source code. It is written as a rebuild reference: every rule, regular expression, threshold, file name and user-visible text that affects behaviour is listed. Requirement IDs AR-x (Android Requirement) are new; where a requirement ports a desktop requirement the desktop ID is given as (FR-x).

1. Purpose and scope

1.1 Problem

Dashcams (Vietmap, Xforce, 70mai, …) record 1-, 3- or 5-minute clips per camera (a camera setting), e.g. 20260924070830_0001446F.MP4 (Front) and 20260924070830_0001447R.MP4 (Rear). Watching a trip means opening dozens of files. The desktop tool (Windows, Python + ffmpeg) joins them; this app does the same on the phone, directly from the dashcam's SD card (or a card reader on USB-OTG), without a PC.

1.2 What the app does

  1. The user picks the dashcam folder (input) and optionally a different output folder (typical use: input on the SD card, output in the phone's Movies/).
  2. The app finds all clips, works out which camera each clip belongs to, orders them in time, and shows a plan: which output files will be written, from how many clips, total duration and size, and warnings (gaps, unreadable files, space).
  3. On Merge, each camera's clips are joined into one MP4 per trip part losslessly (compressed samples are copied, never decoded or re-encoded).
  4. Each output is verified (duration and size) before it gets its final name, and a merge_report.txt is written next to the outputs.

1.3 Non-goals (deliberately not built)

  • No re-encoding, trimming, overlays, speed-up, or format conversion.
  • No deletion of source clips (desktop FR-12 --delete-source is not ported). The app never deletes any file.
  • No config.json, no user-defined camera profiles, no CLI, no parallel merge jobs.
  • No background/foreground service: merging runs while the app is open (screen kept on).
  • No network access, no analytics, no storage permissions.

3. Functional requirements

3.1 Folder selection and access

  • AR-1.1 The user selects the input folder with the system folder picker (ACTION_OPEN_DOCUMENT_TREE). Any provider the picker offers may be used; the supported and tested one is external storage (phone storage, SD card, USB-OTG card reader).
  • AR-1.2 On selection the app takes a persistable read+write URI permission and stores the tree URI in preferences, so the choice survives restarts.
  • AR-1.3 The user may select a separate output folder the same way (read+write, persisted). A Use default button clears it.
  • AR-1.4 Output location rule:
  • no output folder chosen → <input folder>/merged (created if missing; an existing child named merged in any letter case is reused);
  • output folder chosen and it is the same tree as the input (same tree document ID) → treated as "not chosen" (default merged/ subfolder);
  • otherwise → files are written directly into the chosen folder (no subfolder).
  • AR-1.5 Folders are shown as Phone: /<path> for the primary volume and SD card/USB (<volume-id>): /<path> for other volumes, derived from the tree document ID <volume>:<path> (e.g. 1721-8D53:Vietmap_M1/Movie).
  • AR-1.6 Changing input or output folder resets the session to Idle (discarding any shown plan).

3.2 Scanning (FR-1)

  • AR-2.1 The input tree is walked recursively (breadth-first) with DocumentsContract child queries (DOCUMENT_ID, DISPLAY_NAME, MIME_TYPE, SIZE, LAST_MODIFIED).
  • AR-2.2 A file is a clip when its extension (case-insensitive) is one of mp4, mov, ts, mkv, 3gp. (.avi from the desktop list is excluded: Android's MediaExtractor cannot read it.)
  • AR-2.3 Skipped: any sub-folder named merged (case-insensitive) (FR-1.3); the output folder itself if it lies inside the input tree (matched by document ID) (FR-1.3); any file whose name starts with INCOMPLETE_DO_NOT_USE_ (FR-1.4).
  • AR-2.4 Each clip records: document URI, file name, parent folder name, size in bytes, last-modified time (ms). Scan results are sorted by lower-cased URI for determinism.
  • AR-2.5 No clips found → state Error, status No video files found, text No mp4/mov/ts/mkv/3gp files in this folder or its subfolders. (FR-1.5)
  • AR-2.6 The output folder is opened (and merged/ created if needed) at the start of the scan, before any clip is read.

3.3 Camera detection (FR-2)

  • AR-3.1 Built-in profiles are tried in this order; the first profile that labels ≥ 90 % of all clips wins (FR-2.2). Matching is case-insensitive; "name" profiles match the file name, "parent" profiles match the containing folder name. The token captured in group cam is upper-cased and looked up in the profile's map; a clip counts as matched only if the token is in the map.
# Profile Scope Token → camera
1 Xforce name F→Front, R→Rear
2 SuffixLetter name F, A→Front; R, B→Rear; I→Interior
3 Word name FRONT→Front; REAR, BACK→Rear; INSIDE, INTERIOR, CABIN→Interior
4 CamN name 1→Front, 2→Rear, 3→Interior
5 70mai name F→Front, B→Rear
6 Folder parent FRONT, F, NORMAL→Front; REAR, R, BACK, B→Rear; INTERIOR, INSIDE, CABIN, I→Interior

Regular expressions (Java syntax, compiled with Pattern.CASE_INSENSITIVE, applied with find()), exactly as used:

1 Xforce        ^(?<ts>\d{14})_(?<seq>\d+)(?<cam>[FR])\.(?:mp4|mov)$
2 SuffixLetter  _(?<cam>[FRABI])\.[A-Za-z0-9]+$
3 Word          (?<cam>FRONT|REAR|BACK|INSIDE|INTERIOR|CABIN)
4 CamN          CAM(?<cam>[1-3])
5 70mai         ^(?:NO|EV|PA)?\d{4}[-_]?\d{4}[-_]\d{6}[-_]\d+(?<cam>[FB])\.[A-Za-z0-9]+$
6 Folder        ^(?<cam>front|f|normal|rear|r|back|b|interior|inside|cabin|i)$
  • AR-3.2 The Xforce profile also sets the clip's timestamp from group ts (yyyyMMddHHmmss) and its sequence number from group seq. Vietmap M1 files (20260924070830_0001446F.MP4) match this profile.
  • AR-3.3 Before each profile is tried, all labels are reset to Unclassified.
  • AR-3.4 Manual mapping (FR-2.3): if no profile reaches 90 %, clips are grouped by a token and the user assigns each token to Front / Rear / Interior / Skip:
  • if the clips live in more than one folder, token = folder:<parent folder name>;
  • otherwise token = the letters immediately before the extension (regex ([A-Za-z]+)\.[A-Za-z0-9]+$, upper-cased), or ALL if there are none.
  • Tokens are listed sorted. Tokens the user leaves unassigned become Unclassified; Skip clips are ignored silently.
  • AR-3.5 Output groups are built in the order Front, Rear, Interior; groups with no clips are omitted. Unclassified clips are counted in the plan and report but not merged.

3.4 Ordering and gaps (FR-3)

  • AR-4.1 For every clip the file stem (name without extension) is parsed:
  • Timestamp, first valid match of, in order: TS14 = (?<!\d)(\d{4})(\d{2})(\d{2})(\d{2})(\d{2})(\d{2})(?!\d) then TS_SEP = (?<!\d)(\d{4})[-_]?(\d{2})[-_]?(\d{2})[-_T ](\d{2})[-_:.]?(\d{2})[-_:.]?(\d{2})(?!\d). Matches that are not a valid date/time (e.g. month 13) are skipped and the next match is tried. Result is a local date-time (no time zone).
  • Sequence = the last run of 3+ digits (?<!\d)(\d{3,})(?!\d) that does not overlap the timestamp match.
  • Values already set by the camera profile are kept.
  • AR-4.2 Each camera group is sorted by the strongest key that all its clips have (FR-3.1/3.2):
  • all have a timestamp → by (timestamp, sequence or 0, lower-case name);
  • else all have a sequence → by (sequence, lower-case name), warning <Camera>: order based on sequence number in filename;
  • else → by (mtime, lower-case name), warning <Camera>: order based on file modification time, please spot-check (FR-3.3).
  • AR-4.3 Gaps (FR-3.4, FR-3.4a), only for timestamp-ordered groups: for consecutive clips A, B: gap = (B.timestamp − A.timestamp in whole seconds) − A.duration — end of A to start of B, never start-to-start (5-min clips are 300–302 s apart). A.duration is the probed duration; no clip length is assumed (Ordering.gapSeconds returns null and the pair is skipped when it is unknown). A gap > 300 s that does not start a new trip (AR-6.1 rule 2) produces the warning <Camera>: gap of <minutes, 1 decimal> min between <A name> and <B name>.

3.5 Probing (FR-4)

  • AR-5.1 Every clip of every camera group is probed (not sampled), with a pool of 4 worker threads. Progress is shown as Reading <Camera> clips… <done> / <total>.
  • AR-5.2 Probing opens the clip with MediaExtractor.setDataSource(context, uri) and selects tracks:
  • video = first track whose MIME starts with video/;
  • audio = first audio/ track if its MIME is muxable (audio/mp4a-latm (AAC), audio/3gpp (AMR-NB), audio/amr-wb); if the first audio track is not muxable it is recorded as dropped and no other audio track is considered.
  • AR-5.3 A clip is unreadable (with this reason) when: opening throws (reason = exception message); no video track; video MIME not in {video/avc, video/hevc, video/mp4v-es, video/3gpp} → video codec <mime> cannot be stream-copied to MP4; duration ≤ 0 → no duration (file may be truncated).
  • AR-5.4 Duration = max(video KEY_DURATION, audio KEY_DURATION) in microseconds.
  • AR-5.5 Stream signature (two strings; clips can only share an output if both are equal):
  • video: <mime> <width>x<height> rot<rotation> csd:<h0>/<h1>/<h2>
  • audio: <mime> <sampleRate>Hz <channels>ch csd:<…> or none

where h0…h2 are hex Arrays.hashCode values of the csd-0, csd-1, csd-2 codec config buffers that exist. Including the codec config (SPS/PPS) is required because MediaMuxer takes the track format from the first clip only. - AR-5.6 Description for the plan: H.264|H.265|MPEG-4|H.263 <w>x<h> plus + AAC|AMR|AMR-WB when audio is copied. - AR-5.7 Unreadable clips are removed from their group and listed in warnings as <Camera>: skipped unreadable file <name> (<reason>) (FR-4.5). If a group has dropped audio: <Camera>: audio not copied (<mime> cannot be stored in MP4), video only. If a group ends up empty: <Camera>: no readable clips left, nothing to merge.

3.6 Planning, splitting and naming (FR-3.5, FR-4.4, FR-6)

  • AR-6.1 Walking each ordered group, a new output part starts before clip C when (checked in this priority order):
  • C's signature differs from the current part's signature → reason codec change (FR-4.4);
  • option Split into trips is on (default on), the group is timestamp-ordered, and the gap before C (AR-4.3, computed directly, independent of the 300 s warning threshold) is > the trip gap (default 15 min = 900 s, set on the Setup tab) → trip gap (FR-3.5);
  • option 3.9 GB is on and current part bytes + C's size > 3.9 × 1024³ bytes → max part size (FR-6.8).

A trip is the run of parts between two trip gap splits. Planner.numberTrips gives every part tripIndex/tripCount and tripPart/tripParts (its number within the trip). Codec-change and size splits add the warning <Camera> part <n>: new part started because of <reason>; trip splits add none — the trip list shows them (FR-3.5e). - AR-6.2 Expected duration of a part = sum of its clips' probed durations; expected size = sum of its clips' sizes. - AR-6.3 Output name (FR-6.3): <Camera>_<first>_to_<last>.mp4, with _trip<n> appended when the camera has more than one trip, then _part<m> when that trip has more than one part (numbered within the trip, e.g. …_trip2_part1.mp4, since v1.5; before: _part<n> per camera). <first>/<last> are the first/last clip's timestamp as yyyyMMdd_HHmmss (date and time separated by _, since v1.4), or the clip's file stem if it has no timestamp. Example: Front_20260924_070830_to_20260924_073130_trip1.mp4. - AR-6.5 Plan text (FR-3.5d): one entry per part, <Camera> trip <n>/<N>[ part <m>/<M>]: <yyyy-MM-dd HH:mm:ss> - <HH:mm:ss>, <n> clips, H:MM:SS, <size> (the end keeps its date when it is another day; label and times are left out when unknown), followed by the output name on its own line. - AR-6.4 Collisions (FR-6.2): if the name exists in the output folder, or was already given to another part in this plan, try <stem>_2.mp4, <stem>_3.mp4, … until free. Existing files are never overwritten. - AR-6.5 Each part is first written as <final stem>.partial.mp4.

3.7 Merging (lossless stream copy)

  • AR-7.1 Parts are processed sequentially. For each part:
  • create <stem>.partial.mp4 (MIME video/mp4) in the output folder;
  • open it "rw" and create MediaMuxer(fd, MUXER_OUTPUT_MPEG_4);
  • for each clip in order, open a MediaExtractor, select the same tracks as in probing, and copy samples (below);
  • muxer.stop(); then verify (§3.8).
  • AR-7.2 Muxer set-up happens on the first clip of the part: addTrack with the first clip's video format, then its audio format if audio is copied; setOrientationHint(KEY_ROTATION) if the video format carries a rotation; start().
  • AR-7.3 Timestamp algorithm (per clip):
  • base = the extractor's first sample time after selecting the tracks (clamped ≥ 0), i.e. the earliest sample of the clip;
  • offset = running output time, starting at 0 for the part;
  • each sample is written with pts_out = offset + (pts_in − base), unchanged bytes, BUFFER_FLAG_KEY_FRAME iff the extractor reports SAMPLE_FLAG_SYNC;
  • audio only: if pts_out ≤ the previous audio pts_out, use previous + 1 µs (keeps audio strictly increasing across clip joins);
  • per track remember the last sample-to-sample delta; the clip's end = max over samples of (pts_in − base + delta_of_that_track);
  • after the clip: offset += clip end.

Samples are read in the file's own interleaving order (both tracks selected on one extractor), so the output interleaving mirrors the source. - AR-7.4 Sample buffer: one direct ByteBuffer of 16 MiB (enough for a 4K keyframe). - AR-7.5 Cancellation is checked before each clip and before each sample. On cancel or any exception the muxer is released and the partial file is kept and renamed to INCOMPLETE_DO_NOT_USE_<final stem>.mp4 (_2, _3… if taken) (FR-6.5). If that rename fails the file keeps its .partial.mp4 name. - AR-7.6 Progress = bytes of samples copied / total expected bytes of all parts, UI updated at most every 200 ms. Status line: Part <i>/<n>: <output name>.

3.8 Verification (FR-7)

  • AR-8.1 After stop(), the partial file is re-opened with MediaExtractor; its duration is the max KEY_DURATION across its tracks.
  • AR-8.2 PASS requires both:
  • |actual − expected| ≤ max(1.0 s, 0.1 % × expected); and
  • actual size ≥ 90 % of the summed source sizes.
  • AR-8.3 PASS → rename .partial.mp4 → final name (FR-6.4). FAIL → rename to INCOMPLETE_DO_NOT_USE_… with reason(s): output cannot be read back, duration <a>s vs expected <e>s, size <n> < 90% of <m> (joined with ;).
  • AR-8.4 After all parts: every source clip is re-queried; a clip that is missing or whose size changed is reported as <name>: changed or missing and the report shows Sources untouched: CHANGED (FR-7.6). (Android checks size only, not mtime.)

3.9 Report (FR-9)

  • AR-9.1 merge_report.txt (UTF-8, \n) is written into the output folder after every merge run (replacing an earlier report there). Format:
Front trip 1/2: Front_20260924_070830_to_20260924_073130_trip1.mp4
    24 files, 0:23:07, 2.33 GB  ->  PASS
Rear trip 1/2: Rear_20260924_070830_to_20260924_073130_trip1.mp4
    24 files, 0:23:07, 1.60 GB  ->  PASS
Unclassified: 0   Skipped unreadable: 0   Sources untouched: OK
Output folder: Phone: /Movies/DashMerged

The per-part label is trip <n>/<N>[ part <m>/<M>], or part <n> when the camera has a single trip. The 494.6 min break that separated the two trips is not a warning (AR-4.3).

For non-PASS parts the status is followed by (<reason>) and the file name is the INCOMPLETE_… name. A Source problems: section appears when AR-8.4 found any. When the user unticked parts (AR-10.12), the per-part lines are followed by Not selected (skipped by user): <m> and one line per skipped output name, indented 4 spaces. - AR-9.2 Formats: duration H:MM:SS (rounded seconds); size x.xx GB (≥ 1 GiB), x.x MB (≥ 1 MiB) else x.x KB, 1024-based, . decimal separator. - AR-9.3 The same text is shown on screen when the run finishes.

  • AR-10.2 Free space: for the external-storage provider (com.android.externalstorage.documents) the volume is the part of the output folder's document ID before :; free bytes = StatFs(<path>).availableBytes with path = Environment.getExternalStorageDirectory() for primary, else /storage/<volume>. If unknown, the line is omitted. (The provider's roots table is not usable: it needs a system permission.)
  • AR-10.3 If the summed expected size of the selected parts (AR-10.9) > free space, the selection card shows (in the error colour) NOT ENOUGH SPACE: needs about <x>, only <y> free in the output folder. Free up space or choose another output folder. The Merge button is still offered (the user decides).
  • AR-10.4 A plan with zero parts → state Error, status Nothing to merge.

Choosing which files to export (v1.1)

  • AR-10.5 Selection list. In state Planned, above the plan text, a card Files to export lists one row per planned output part: checkbox, <Camera> trip <n>/<N> (bold), <start> - <end> (AR-6.5), <n> clips, H:MM:SS, <size>, the output file name, and ▲ / ▼ buttons (AR-10.17). The rows are one flat list in export order (AR-10.14). Above them is one tri-state box per camera present, shown as <Camera> (<ticked>/<n>), in CAMERA_ORDER.
  • AR-10.6 Default. Right after a successful plan every part is ticked, so tapping Merge immediately behaves exactly like v1.0.
  • AR-10.7 Bulk controls. Buttons Select all (disabled when all are ticked) and Select none (disabled when none are ticked). Each camera header has a tri-state checkbox (on / off / some); tapping it ticks all of that camera's parts, or unticks them all when they were all ticked.
  • AR-10.8 Summary and Merge gating. A line Selected: <k> of <n> file(s), <size> (size = sum of the selected parts' expected sizes) updates live. Merge is enabled only when k ≥ 1. Status text in Planned: Plan ready - choose files, then tap Merge.
  • AR-10.9 Free space on the selection. AR-10.3 is evaluated on the selected parts and updates as the selection changes. The plan text keeps the Free space there: line.
  • AR-10.10 Merge only the selection. Merge processes only the ticked parts, in plan order. Progress, the Part i/k labels and the Done/Cancelled/Finished status counts use k = number of ticked parts. The source-unchanged check (FR-7.6) covers the clips of the ticked parts.
  • AR-10.11 Stable names. Output names are the ones computed at plan time (AR-6.3, AR-6.4) and are not recomputed when parts are unticked. For example, _part2 may be written without _part1. Unticked parts write nothing.
  • AR-10.12 Report. See AR-9.1: skipped parts are listed under Not selected (skipped by user):.
  • AR-10.13 Lifetime. The selection is held in MergeSession, so it survives a screen rotation. Every new plan resets it to "all ticked". It is cleared by Scan & plan, a folder change and reset(). Edits are ignored outside Planned.

Export order and Front/Rear pairing (v1.2)

  • AR-10.14 Export order. MergeSession.order is a permutation of the plan's part indices. The list shows parts in this order, and Merge writes the ticked ones in this order (the report lists results in the same order, then the skipped ones). It is rebuilt from the current sort mode on every new plan.
  • AR-10.15 Sort mode. Chips Order: By camera | By time (preference order_by_time, default By time since v1.5 — Front and Rear of a trip together, as on the PC). Choosing one re-sorts the list immediately and drops manual moves.
  • By camera = plan order: Front parts, then Rear, then Interior, each in time order.
  • By time = by part start (first clip's timestamp); same start → CAMERA_ORDER, so the Front and Rear file of one trip sit together (Front 1, Rear 1, Front 2, Rear 2). Parts without a timestamp go last, by part number then camera.
  • AR-10.16 Keep Front/Rear pairs together. Switch Keep Front/Rear pairs together (same time) (preference link_pairs, default off). Two parts of different cameras are partners when their time ranges overlap: range = [first clip timestamp, last clip timestamp + last clip duration (0 if unknown — no length is assumed)). When neither part has a timestamp, parts with the same part number are partners; a part with a timestamp is never paired with one without. With the switch on, ticking or unticking a row applies the same state to its partners. Select all, Select none and the camera boxes are not affected by the switch.
  • AR-10.17 Manual order. ▲ swaps a row with the one above and ▼ with the one below (disabled on the first and last row respectively).

3.11 Write safety (FR-8)

  • AR-11.1 One class, OutputFolder, is the only code that creates, writes or renames files. It has no delete method; nothing in the app deletes files.
  • AR-11.2 It creates files only as direct children of the output folder; names containing / are refused; creating a name that already exists is refused; if the provider silently changes the name (e.g. adds (1)), it is reported as an error.
  • AR-11.3 It renames only documents it created during this run (tracked set of URIs). The one exception is merge_report.txt, which may be an existing file it opens with mode "wt" (truncate) to replace.
  • AR-11.4 Source clips are only ever opened for reading (MediaExtractor, queries).

3.12 Options (persisted)

5.3 Pipeline (MergeSession)

Mirrors desktop pipeline.run():

  1. Scan (background thread): open output folder → scan input (skip output folder) → Cameras.detect → if no profile: NeedCameraMap and stop.
  2. Plan: Planner.buildPlan (group → annotate → order → probe all → drop unreadable → gaps → split → name) → free-space check → plan text → Planned.
  3. Confirm & select: the user reads the plan, ticks the files to export (state planParts, selected = indices into plan.parts, order, orderByTime, freeBytes; edited via toggle(i, linked), setCamera, selectAll, selectNone, arrange(byTime), move(pos, delta); pure helpers in core/Arrange.kt) and taps Merge (the explicit FR-2.4 step).
  4. Merge (background thread): for each ticked part, in order Merger.mergePart (write partial → verify → rename) → source check → write report → Done.

MergeSession is a process-level singleton holding Compose mutableStateOf fields, so a configuration change does not lose a running merge (the activity additionally declares configChanges="orientation|screenSize|screenLayout|keyboardHidden"). Worker threads post all UI-state changes to the main looper. Cancellation is an AtomicBoolean.

7. Error handling and edge cases

Situation Behaviour
Folder permission revoked / card removed Exception in scan or merge → Error with the exception message; files already finished stay.
Clip cannot be opened / truncated Listed as unreadable, skipped, rest merged (AR-5.7).
Unsupported audio (e.g. PCM .mov) Video-only output, warning.
Codec/resolution change mid-trip New part (codec change).
Output name exists _2, _3…
Leftover <name>.partial.mp4 from a crashed run createFile refuses to overwrite → Error for the run; rename or remove that file manually, then rescan.
Output larger than 4 GiB on FAT32 target Write fails → part FAIL, kept as INCOMPLETE_…; use the 3.9 GB switch.
Not enough space Plan warning; if merged anyway, the write fails → INCOMPLETE_….
App closed / killed mid-merge Partial file stays as ….partial.mp4 (no final name, never mistaken for a good file).
Cancel Current part → INCOMPLETE_…; remaining parts not started; report written.

8. Known limitations

  • Merging runs in the foreground only; leaving the app for long may let Android stop it.
  • Throughput is bounded by the SD card / USB reader (observed ≈ 0.5 GB per minute for SD → phone on the Note 10: 9.4 GB in about 15 minutes).
  • B-frame streams are copied in decode order with their original timestamps; typical dashcam streams (no B-frames / fixed GOP) are the tested case.
  • The audio track may start a few milliseconds offset at clip joins (per-clip rebase uses the earliest sample of the clip); not audible in tests.
  • Only the external-storage provider reports free space.
